PumpkinPie

A Minecraft 26.2 server written in Rust, built for vanilla behavioural parity.

What this is

PumpkinPie is a Minecraft: Java Edition server for 26.2. It began as a fork of Pumpkin and has grown into its own project with its own priority: matching what vanilla actually does. Every change is checked against a decompiled 26.2 server, and where it can be, confirmed against a running server with a real client attached rather than by reading code alone.

That is the difference in practice. Recent work fixed freezing damage applied five times over, fire resistance that ignored fireballs, hoppers running eleven percent slow, comparators reading the wrong signal from their side inputs, and a registry encoding that made strict clients refuse to join. Each fix cites the vanilla source it was checked against in the commit history.

Verify what you downloaded

Check the archive against the published checksum before running it:

sha256sum -c SHA256SUMS --ignore-missing
On virus scanners. These binaries are unsigned, so Windows SmartScreen and some antivirus products will warn about them — that is what an unsigned executable from a small project looks like, not evidence of anything in particular. Every release links a VirusTotal report for its archives so you can read the scan results yourself, and building from source is always available if you would rather not take a binary on trust.

Running it

tar xzf pumpkinpie-x86_64-unknown-linux-gnu.tar.gz
cd pumpkinpie
./pumpkin

The server writes pumpkin.toml on first start. It speaks the 26.2 protocol; older clients are not supported.

Read the rows together. The last one disagrees with the first two, and that is the interesting part. PumpkinPie covers the most of vanilla and matches the most methods outright. SteelMC matches a higher share of what it takes on, because it takes on less: its percentage is over 5423 methods where PumpkinPie's is over 8572. A project implementing fewer classes scores higher per class while covering less of the game, so no one number settles it. Against the upstream it forked from, PumpkinPie leads on every measure here.

Two caveats. The instrument carries 18 negative-control probes; only 9 apply to SteelMC, and upstream needed --no-probes because one failed against its layout, so cross-repo confidence is weaker than same-repo confidence. And this is name-level matching: it does not prove any of the three behaves correctly.

Parity, measured

Two instruments, deliberately separate, because they answer different questions. Both are in-repo and reproducible against the 26.2 decompile.

Registry coverage: does an implementation exist at all?

coveredtotal
Blocks990119682.8%
Items1421153792.5%
Entities158158100%
Total2569289188.9%

That block figure understates things. Auditing all 206 uncovered blocks against Blocks.java found 185 that need no behaviour at all — wool, concrete and dyed terracotta are literally (c, p) -> new Block(p) — and 21 that are data-driven. Exactly one was a real gap. The item list is the same story: of 118 uncovered items, 80 were inert crafting materials, 20 client-only tooltip subclasses, 14 data-driven, and 4 real. Counting only registrations that should exist puts both near 99%.

Method-level conformance: how much of each class's surface is covered?

Strict, counterpart in the one mapped file22.4%
Loose, counterpart anywhere in crates/52.5%
Remaining leads4068

The truth is between the two: strict under-credits behaviour split across modules and trait impls, loose over-credits trait defaults. And a lead is not a confirmed gap — measured yield runs around one in five, the rest being renames, methods inlined into their callers, or client-only code a dedicated server never reaches. Audits so far: 1 real gap in 207 block leads, 3 in 14 worldgen leads, 4 in 118 item leads, 1 in 30 protocol leads.

Neither number is behavioural proof. The implementation tracker counts surface, not behaviour — a matched method can still behave differently, which is what the ongoing verification work is for.
